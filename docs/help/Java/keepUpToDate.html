Keeping Bar History Up to Date

Brief

The article describes how to keep a bar history up to date.

Details

When the price history is requested "up to now", "now" is the moment when the server has received the request. If the application needs to keep that history up to date, it must use updates of the offers table in ForexConnect and build further history using tick data.

Adding new ticks

The algorithm of adding new ticks to a bar history is quite simple. When a new tick arrives (i.e. offers table is updated for a particular instrument):

  • Check whether the new tick belongs to the last bar of the history. The application can use the CandlePeriod class to calculate the date and time of a bar of a specified size to which the tick date and time belong.

    To do that, you need to:

    • Calculate the bar start and end time using the CandlePeriod.getCandle() method and passing the date/time of a tick and timeframe of the bar collection as the parameters.

    • The tick belongs to a bar if the bar (or candle, which is the same in this context) start time returned by the getCandle() method is equal to the start time of the last bar.

  • If the tick belongs to the current bar, the high, low, and close prices of the bar must be updated as follows:

    • The close price is set to the tick value.

    • If the tick value is greater than the high value, the high value is set to the tick value.

    • If the tick value is less than the low value, the low value is set to the tick value.

  • If the tick does not belong to the current bar, a new bar must be created as follows:

    • The date and time of the bar must be equal to the date and time of the bar start returned by the getCandle() method.

    • The high, low, and close prices must be equal to the tick price.

    • The open price calculation depends on the application and/or server settings. There are two options:

      • The open price of the bar is equal to the close price of the previous bar (this option is default for all servers).

      • The open price is equal to the first tick that occurred inside the bar.

Handling the gap between the time the server received the request and the time the response is handled on the client's side

Preparing the requested data, delivering it to the client and parsing the data on the client's side can take some time. As the server takes the data only to the moment when the request is received, a number of ticks can occur before the client gets the result.

To avoid this:

  • At the same moment when the request is sent to the server, the application should start collecting all ticks for the instrument.

  • When the response is handled by the client, all of the collected ticks must be added to the history by the algorithm described above.

  • And then all forthcoming will be handled in a regular manner.

Tick filtering and tick volume handling

Because of a huge amount of ticks, unreliable nature of the client connection and big diversity of the performance of the client equipment, every single tick cannot be delivered to the client. The whole system is designed to provide the most fresh ticks rather than all ticks to the client. The filtering algorithm, however, keeps the first and the last ticks of every minute, the current minute maximum and the current minute minimum ticks, so the algorithm described above will produce the correct open, high, low, and close prices of any bar even if a few ticks have been filtered out.

The problem is the tick volume. As some ticks are filtered out, the client application can not simply count updates of the offers table in order to calculate the tick volume. To make this algorithm work, the server also broadcasts accumulated tick volume for a minute to which the tick belongs (see the volume column of the offers table or the IO2GOfferRow.getVolume() method).

To update a 1-minute tick volume of a candle, the application should simply replace the tick volume value with the value received in the offer table update.

To update larger candles, the application must use the following algorithm:

  • For the last candle, the application must keep the latest received accumulated volume for the last minute and date/time of a minute.

  • If a new offer update belongs to the same minute as the previous offer update, the previously received accumulated volume must be subtracted from the tick volume of the bar and newly received accumulated volume should be added.

  • If a new offer update belongs to the new minute, the accumulated volume must be simply added to the bar volume.

In order to get the initial data for the collections that are just received from the server, use the getLastBarVolume() and getLastBarTime() methods of the reader. These methods return the latest minute at the moment the collection is calculated on the server and the accumulated minute volume at this moment.
